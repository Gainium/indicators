# 002. McGinley Dynamic indicator

Feature spec — new indicator, no existing behaviour is being changed.

## §1 Behaviour

A new adaptive moving-average indicator, **McGinley Dynamic** (`IndicatorEnum.mg`
= `'MG'`), computed from a single price source (close) and a `length`
parameter.

- On the first candle it has ever seen, the indicator's value equals that
  candle's close price.
- On every subsequent candle, the value moves toward the new close, but the
  *speed* of that movement is not fixed the way a plain EMA's is — it
  accelerates when price is moving fast relative to the indicator's current
  value, and decelerates when price is close to it. This is what makes it
  track price more tightly than a fixed-period average, with less lag,
  while still smoothing noise.
- The indicator is mathematically defined on every candle from the first one
  onward — there is no multi-candle blackout the way an SMA-seeded EMA has
  before its first real value. See §3 for whether the platform should still
  impose a stabilization buffer before treating the value as trustworthy.

## §2 Formula

Source of truth: the requester's Pine Script.

```
mg[0] = close[0]
mg[n] = mg[n-1] + (close[n] - mg[n-1]) / (length * (close[n] / mg[n-1])^4)
```

This matches TradingView's `ta.ema` seeding behaviour — Pine's own reference
implementation of `ta.ema` seeds directly with the source value on the first
bar (`na(sum[1]) ? src : ...`), not with an SMA of the first `length` bars.
Reusing this repo's existing `EMA` class as a seed would be **wrong** — that
class deliberately delays its first value until `length` bars have
accumulated (SMA-style seed), which does not match what `ta.ema` (and
therefore this Pine Script) actually does on bar 1.

## §3 Open questions

- **Warmup candle count for `getWarmupCandles`.** The formula is
  mathematically defined from bar 1, so a "true" warmup could be 1. But
  every other single-value moving-average indicator in this factory
  (`IndicatorEnum.ma`) reports a large buffer (`interval + 300`) so
  downstream consumers get a stabilized value rather than a
  mathematically-valid-but-still-adapting first read. Left to the plan to
  decide a concrete number.
- **Is this an alias of an existing `MAEnum` variant, not a new
  indicator?** Checked: `IndicatorEnum` (`src/types/config.ts`) has no
  `mg`/`mcginley` entry, and `MAEnum` (`ema`/`sma`/`wma`/`dema`/`tema`/
  `vwma`/`hma`/`rma`/`price`) has no shape that reduces to this formula —
  none of those are self-referential with a `(price/prev)^4` feedback term.
  Verdict: **not an alias** — this needs its own `IndicatorEnum` entry and
  its own `LightIndicator` subclass.

## §4 Non-goals

- No child indicator (no `ATR`, no nested `LightIndicator`) — the formula
  only needs the current close and the indicator's own previous output.
- Not a filter (Session-style, time/calendar-based) — this is a real
  candle-driven signal, so per the new-indicator-integration skill's Step 0
  fork it needs **full factory registration** (`create`/`warmup`/`feed`),
  not the filter's pure-function-only shape.

## §5 Cross-repo scope (this repo's slice)

This spec covers only the `@gainium/indicators` package — the math + factory
registration. Consumption by `app-sh` (bot engine, GraphQL, public v2 API)
and `main-dash-sh` (chart study, bot-settings catalog) are separate specs in
those repos, gated by this repo's version being published first.
